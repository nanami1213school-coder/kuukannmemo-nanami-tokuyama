# アプリ開発全体の工程

本プロジェクトでは、以下の工程に沿ってアプリの設計・開発を進める。

```text
企画・前提確認
    ↓
要件定義
    ↓
要件定義書の作成
    ↓
基本設計
    ↓
基本設計書の作成
    ↓
詳細設計
    ↓
詳細設計書の作成
    ↓
テスト設計
    ↓
実装
    ↓
テスト・修正
    ↓
提出資料の作成
```

## 1. 企画・前提確認

アプリの制作を始める前に、課題の条件や開発上の制約を確認する。

### 確認項目

- アプリ名
- 制作目的
- 解決したい問題
- 対象ユーザー
- 対応端末
- 対応OS
- 制作期限
- 制作人数
- 使用する技術
- 使用できる外部サービス
- 費用条件
- 必須提出物

### 成果物

- 制作条件一覧
- 提出物チェックリスト

## 2. 要件定義

要件定義では「どのようなアプリを作るのか」を明確にする。

この段階では、画面の細かいレイアウトやプログラムの実装方法までは決めない。

### 2.1 アプリ概要

以下の内容を整理する。

- どのようなアプリか
- 誰が使用するか
- どのような問題を解決するか
- アプリを使用すると何ができるか

### 2.2 対象ユーザー

アプリを利用する人物を明確にする。

必要に応じて、年齢、利用目的、利用環境なども整理する。

### 2.3 利用シーン

ユーザーが、いつ、どこで、どのようにアプリを使用するかを整理する。

### 2.4 機能の洗い出し

アプリに必要と思われる機能をすべて挙げる。

この時点では実装の難易度を気にせず、必要な機能を整理する。

### 2.5 MVPの決定

洗い出した機能を、以下のように分類する。

- 今回必ず実装する機能
- 時間に余裕があれば実装する機能
- 将来実装する拡張機能
- 今回は実装しない機能

MVPは、アプリの目的を達成できる最小限の完成版とする。

### 2.6 機能要件

ユーザーがアプリ上で実行できることを機能ごとに整理する。

機能要件は、原則として「対象＋動作」の形で記載する。

例：

- 部屋を登録する
- メモを保存する
- 登録済みの情報を表示する

### 2.7 非機能要件

機能以外に必要となる品質や条件を整理する。

- 操作性
- 表示速度
- セキュリティ
- プライバシー
- 対応端末
- 対応OS
- データ保存
- データ同期
- 通信できない場合の動作
- 外部サービスの可用性

### 2.8 制約条件

開発時に守る必要がある条件を整理する。

- 使用する言語
- 使用するフレームワーク
- 使用する外部サービス
- 費用の上限
- 制作期間
- 対応端末
- 提出形式

## 3. 要件定義書の作成

要件定義で決めた内容を、一つの文書としてまとめる。

### 要件定義書の構成

1. アプリ概要
2. 制作の背景
3. 制作目的
4. 対象ユーザー
5. 利用シーン
6. 機能一覧
7. MVPの範囲
8. 機能要件
9. 非機能要件
10. 制約条件
11. MVP外の拡張機能
12. アプリの完成条件

### 完成条件

アプリが完成したと判断するための条件を、確認可能な形で定義する。

例：

> ユーザーが部屋を登録し、部屋の写真上にメモを保存して、後から内容を確認できること。

## 4. 基本設計

基本設計では、要件定義で決めた内容を「どのような仕組みで実現するか」に変換する。

## 4.1 システム構成設計

アプリ、データベース、認証、外部サービスなどの関係を整理する。

### 記載項目

- モバイルアプリ
- 認証サービス
- データベース
- 画像保存サービス
- REST API
- 各システム間のデータの流れ

## 4.2 画面一覧

アプリに必要な画面を洗い出す。

各画面について、以下の項目を整理する。

| 項目 | 内容 |
|---|---|
| 画面名 | 画面の名称 |
| 目的 | 画面を使用する目的 |
| 表示項目 | 画面に表示する情報 |
| 操作内容 | ユーザーが行える操作 |

## 4.3 画面遷移図設計

画面間の移動を図で整理する。

### 記載内容

- 遷移元の画面
- 遷移先の画面
- 遷移のきっかけとなる操作
- 条件によって分かれる遷移

主要な画面遷移を優先し、保存、キャンセル、戻るなどの細かい遷移は必要に応じて省略する。

## 4.4 モバイルUI設計

各画面の大まかなレイアウトを作成する。

### 設計項目

- タイトルの位置
- ボタンの位置
- 入力欄の位置
- 写真の表示位置
- 一覧の表示方法
- ナビゲーション
- 色
- 文字サイズ
- 余白
- アイコン

この段階では、ワイヤーフレームや画面モックを作成する。

## 4.5 扱うデータの整理

アプリ内に登場する「名詞」を探し、必要なデータを洗い出す。

例：

- ユーザー
- 部屋
- メモ
- 写真
- 共有メンバー

## 4.6 データ関連図

データ同士の関係をER図などで表す。

### 確認項目

- 一つのユーザーはいくつのデータを持つか
- 一つの部屋はいくつのメモを持つか
- データ同士をどのIDで関連付けるか
- データを所有するユーザーは誰か
- データを共有できるユーザーは誰か

## 4.7 API一覧

アプリが使用するAPIを一覧にする。

基本設計では、以下の項目を整理する。

| 項目 | 内容 |
|---|---|
| API名 | APIの名称 |
| 目的 | APIを使用する目的 |
| URL | APIのURL |
| HTTPメソッド | GET、POST、PATCH、DELETEなど |
| 認証 | 認証が必要かどうか |

## 4.8 権限設計

ユーザーの種類によって実行できる操作を整理する。

例：

- 未ログインユーザー
- ログイン済みユーザー
- 部屋の所有者
- 共有ユーザー

### 確認項目

- データを閲覧できるユーザー
- データを登録できるユーザー
- データを編集できるユーザー
- データを削除できるユーザー
- 共有設定を変更できるユーザー

## 5. 基本設計書の作成

基本設計で決めた内容を、一つの設計書としてまとめる。

### 基本設計書の構成

1. システム構成図
2. 機能要件
3. 画面一覧
4. 画面遷移図
5. モバイルUI設計
6. データ関連図
7. API一覧
8. 権限一覧
9. 非機能要件
10. 使用技術一覧

## 6. 詳細設計

詳細設計では、基本設計の内容を実装できるレベルまで具体化する。

## 6.1 画面詳細設計

各画面について、以下の項目を定義する。

- 使用するUI部品
- 表示するデータ
- 入力項目
- 初期表示
- ボタンを押したときの処理
- 入力チェック
- エラーメッセージ
- 読み込み中の表示
- データが存在しない場合の表示
- 画面遷移条件

## 6.2 データ詳細設計

各データについて、以下の項目を定義する。

| 項目 | 内容 |
|---|---|
| 項目名 | データの名前 |
| 型 | String、Int、Double、Date、Boolなど |
| 必須 | 必須項目かどうか |
| 初期値 | 最初に設定される値 |
| 説明 | データの用途 |
| 関連 | 他のデータとの関係 |

## 6.3 API詳細設計

各APIについて、以下の項目を定義する。

- API名
- URL
- HTTPメソッド
- 認証の有無
- パスパラメータ
- クエリパラメータ
- リクエスト内容
- レスポンス内容
- 成功時のステータスコード
- エラー時のステータスコード
- エラーメッセージ

## 6.4 処理フロー設計

複数の処理が関係する機能について、処理順序を整理する。

例：

- アカウント登録
- ログイン
- 部屋登録
- 写真アップロード
- メモ登録
- データ同期
- 部屋共有
- アカウント削除

## 6.5 セキュリティ設計

ユーザー情報や共有データを安全に扱う方法を決める。

### 確認項目

- 認証済みユーザーだけがデータを操作できること
- 所有者と共有メンバーだけが部屋を閲覧できること
- パスワードをデータベースへ保存しないこと
- API Secretをアプリ内へ保存しないこと
- 他人のデータを直接取得できないこと
- 通信にHTTPSを使用すること
- アカウント削除時のデータ処理

## 6.6 エラー設計

発生が予想されるエラーと、その際の動作を定義する。

例：

- ログインに失敗した場合
- 通信に失敗した場合
- 写真アップロードに失敗した場合
- 必須項目が未入力の場合
- 共有相手が見つからない場合
- データの同期に失敗した場合
- 外部サービスが利用できない場合

## 7. 詳細設計書の作成

詳細設計で決めた内容を、実装時に参照できる文書としてまとめる。

### 詳細設計書の構成

1. 画面詳細設計
2. データ項目定義
3. API詳細設計
4. 処理フロー
5. 入力チェック
6. エラー処理
7. 認証・権限設計
8. セキュリティ設計
9. 外部サービス連携
10. データ保存・同期方法

## 8. テスト設計

実装した機能を確認するためのテスト項目を作成する。

### テストの種類

- 正常系テスト
- 異常系テスト
- 画面表示テスト
- 画面遷移テスト
- 入力チェックテスト
- データ保存テスト
- 認証テスト
- 権限テスト
- 同期テスト
- 外部サービス連携テスト

### テスト項目の例

- 正しい情報でアカウント登録できる
- 間違ったパスワードではログインできない
- 部屋とメモを保存できる
- アプリを再起動してもデータを確認できる
- 別端末で同じデータを確認できる
- 共有していないユーザーは部屋を閲覧できない
- 写真のアップロード失敗時にエラーが表示される
- 必須項目が未入力の場合は保存できない

## 9. 実装

詳細設計書をもとに、機能を小さな単位に分けて実装する。

### 実装順序

1. プロジェクト作成
2. 共通デザイン作成
3. データモデル作成
4. 画面作成
5. 画面遷移
6. Firebase Authentication連携
7. Cloud Firestore連携
8. Cloudinary連携
9. 共有機能
10. 設定機能
11. エラー処理
12. セキュリティ設定

## 10. テスト・修正

テスト設計書に沿って動作確認を行う。

不具合が見つかった場合は、原因を確認して修正し、再度テストする。

### 確認項目

- 要件どおりに動作するか
- すべての画面へ移動できるか
- データを正しく保存できるか
- エラー時にアプリが停止しないか
- 他人のデータへアクセスできないか
- 複数端末でデータが同期されるか
- 画面が小さい端末でも崩れないか

## 11. 提出資料の作成

課題で指定された形式に合わせて提出物を整理する。

### 提出物の例

- 要件定義書
- 基本設計書
- 詳細設計書
- テスト仕様書
- draw.ioファイル
- 設計書のPDF
- Xcodeプロジェクト
- GitHubリポジトリ
- README
- アプリのスクリーンショット
- 動作確認動画
- 発表資料
