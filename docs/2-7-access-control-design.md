
# 権限設計

## 1. 概要

本書では、空間メモにおけるユーザーの権限と、各機能を利用できる条件を定義する。

## 2. ユーザー区分

| 区分 | 説明 |
|---|---|
| 未ログインユーザー | Firebase Authenticationで認証されていないユーザー |
| ログインユーザー | Firebase Authenticationで認証済みのユーザー |
| owner | 部屋を作成した所有者 |
| editor | 所有者から部屋を共有されたユーザー |

## 3. 権限の判定方法

部屋に対する権限は、次の条件で判定する。

### owner

```text
Room.ownerId == ログインユーザーのuserId
```

### editor

```text
RoomMember.roomId == 対象のroomId
かつ
RoomMember.userId == ログインユーザーのuserId
かつ
RoomMember.role == "editor"
```

`RoomMember`には共有されたユーザーを保存し、部屋の所有者は`Room.ownerId`で判定する。

APIで返す`accessRole`は、これらの情報から生成する。

## 4. 機能別権限

| 操作 | 未ログイン | ログイン | owner | editor |
|---|:---:|:---:|:---:|:---:|
| アカウント登録 | ○ | − | − | − |
| ログイン | ○ | − | − | − |
| ログアウト | − | ○ | ○ | ○ |
| 自分のユーザー情報を確認 | − | ○ | ○ | ○ |
| 部屋を新規登録 | − | ○ | ○ | ○ |
| 所有・共有されている部屋一覧を確認 | − | ○ | ○ | ○ |
| 部屋詳細を確認 | − | − | ○ | ○ |
| 部屋名を変更 | − | − | ○ | × |
| 部屋画像を追加・変更 | − | − | ○ | × |
| メモ一覧を確認 | − | − | ○ | ○ |
| メモ詳細を確認 | − | − | ○ | ○ |
| メモを新規登録 | − | − | ○ | ○ |
| メモを編集 | − | − | ○ | ○ |
| 共有メンバー一覧を確認 | − | − | ○ | × |
| 共有メンバーを追加 | − | − | ○ | × |
| 共有メンバーを削除 | − | − | ○ | × |
| 設定画面を確認 | − | ○ | ○ | ○ |

凡例：

- `○`：操作可能
- `×`：操作不可
- `−`：対象外

## 5. 画面の表示制御

### 部屋一覧画面

- 所有している部屋には「所有」と表示する
- 共有されている部屋には「共有」と表示する
- ログインユーザーが閲覧できない部屋は表示しない

### 部屋詳細画面

ownerには次のボタンを表示する。

- 共有ボタン
- メモ追加ボタン
- 部屋画像追加・変更ボタン

editorには次の操作だけを表示する。

- メモピンの確認
- メモ追加
- メモ編集

editorには、共有管理と部屋画像変更の操作を表示しない。

### 共有管理画面

共有管理画面はownerだけが表示できる。

editorがURLや不正な画面遷移などでアクセスしようとした場合も、処理を拒否する。

## 6. データ別アクセス権限

| データ | 読み取り | 作成 | 更新 | 削除 |
|---|---|---|---|---|
| User | 本人のみ | 本人 | 本人 | 将来機能 |
| Room | owner・editor | ログインユーザー | ownerのみ | 将来機能 |
| Memo | owner・editor | owner・editor | owner・editor | 将来機能 |
| RoomMember | ownerのみ | ownerのみ | ownerのみ | ownerのみ |

画面上でボタンを非表示にするだけではなく、Firestore Security RulesまたはREST API側でも同じ権限を確認する。

## 7. Firebase Authentication

- パスワードはFirestoreに保存しない
- パスワードはFirebase Authenticationで管理する
- FirestoreにはFirebase AuthenticationのUIDを`userId`として保存する
- ログインしていないユーザーからのデータアクセスを拒否する
- ユーザーは自分以外のアカウント情報を変更できない

## 8. Firestore Security Rulesの方針

- `request.auth`が存在することを確認する
- `request.auth.uid`をログインユーザーのIDとして使用する
- クライアントから送信された`ownerId`だけを信用しない
- 部屋を作成するときは`ownerId`が`request.auth.uid`と一致することを確認する
- 部屋を読み取るときはownerまたはeditorであることを確認する
- 部屋を更新するときはownerであることを確認する
- メモを読み書きするときはownerまたはeditorであることを確認する
- 共有情報を変更するときはownerであることを確認する

実際のSecurity Rulesは詳細設計および実装時に作成する。

## 9. メールアドレスによる共有

- 共有相手は登録済みユーザーのメールアドレスで指定する
- メールアドレスは完全一致で検索する
- ユーザー一覧全体をクライアントへ取得させない
- 共有相手の存在確認に必要な情報だけを取得する
- 将来サーバー化した場合は、REST API側でメールアドレスから`userId`を検索する
- ログやエラーメッセージに不要なメールアドレスを出力しない

## 10. Cloudinary

- Cloudinary API Secretをアプリ内に保存しない
- Cloudinary API SecretをGitHubへ登録しない
- MVPでは制限を設定したUnsigned Upload Presetを使用する
- アップロードできる画像形式とファイルサイズを制限する
- 将来はREST APIから署名を発行するSigned Uploadへ移行する
- Firestoreには画像URLとPublic IDだけを保存する

## 11. 不正操作への対応

権限のない操作が行われた場合は処理を実行せず、次のエラーとして扱う。

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "この操作を行う権限がありません。"
  }
}
```

HTTPステータスコードは`403 Forbidden`とする。
